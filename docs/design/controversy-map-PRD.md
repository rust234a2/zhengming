# 跨议题争议地图 PRD

版本 v0.1（实现稿） · 2026-09-12 · 隶属「争鸣」参赛作品 · 实现于 runi-desktop（`?view=map`） · 在线演示 https://zhengming-controversy-map.app.workbuddy.host/

---

## 0. 一句话

把**散落在不同议题下的同一主张**连成一张网——哪些观点反复出现在多个议题里、哪些论点在跨议题地互相反驳，让议题之间的深层分歧结构第一次变得可见。

## 1. 背景与定位

### 1.1 问题：树能表达层级，表达不了"横向共鸣"

「争鸣」先有辩论树（缩进列表 / 无限画布）。树的本质是**层级**：一个节点只有一个 `parentId`，只能表达"A 论点从属于 B 议题"。

但真实讨论里最有价值的洞察往往不是层级的。比如：

- 「AI 只替代执行环节」这一条主张，同时出现在 **6 个**不同议题下（程序员会不会失业、该不该劝人报计算机、该不该学编程……）——它是一条**被反复调用的思想骨架**。
- 「AI 不会消灭程序员」与「计算机毕业生需求持续下降、不应再劝人报考」分属两个不同议题，实质却在**互相反驳**。

这两种关系**在数据结构上就是树无法承载的**：一个节点如果要挂在两个议题下，树就必须把它复制成两份，而复制之后"这两份其实是同一件事"这个信息就永久丢失了。这不是渲染问题，是模型能力边界。

### 1.2 判断标准：为什么不能用"力导向"来复用树的数据

一个反例先排除掉。runi-desktop 早期做过一个 `?view=force` 力导向图，渲染的是**和缩进树完全相同的数据、相同的层级、相同的用途**，唯一区别是节点位置由力学决定而不是由缩进决定。

那份图**是冗余的**。判别标准可以固化为一条设计准则：

> **如果两张图的节点集合与边集合完全相同，只有排布算法不同，那它们是同一个可视化。**

力导向的价值不在"布局好看/会动"，而在于**它能承载树承载不了的节点与边**。所以本 PRD 不做一个"树的力量版"，而是引入两类树里根本不存在的东西：

| 新增 | 树里有吗 | 为什么关键 |
|---|---|---|
| `cluster` 主张簇（**多父**） | ❌ 物理上不可能 | 同一主张横跨 N 个议题，是"跨议题索引"的载体 |
| `bridge` 缝合边 | ❌ | 主张簇 ↔ 议题，横向关系的实体 |
| `rebuts` 冲突边 | ❌ | 跨议题的实质矛盾，最有信息量的关系 |

### 1.3 四层视图分工

「争鸣」的四张图各司其职，**互不替代**：

| 形态 | 载体 | 认知任务 | 一句话 |
|---|---|---|---|
| 缩进树 | `prototypes/debate-tree-prototype.html` | 顺序阅读、快速定位 | 当文档读 |
| 无限画布 | `prototypes/debate-tree-canvas.html` | 自由布局、白板讨论 | 当白板用 |
| 力导向图 | runi-desktop `?view=force` | **单议题内部**对垒结构感知 | 当沙盘看 |
| **争议地图（本 PRD）** | runi-desktop `?view=map` | **议题之间**的横向索引 | 当地图查 |

一句话区分后两者：**力导向图管一个议题内部（正反两军怎么布阵），争议地图管议题之间（哪些主张在跨议题地共鸣或冲突）。**

服务对象也不同。辩论树服务"我要深入这一场"，争议地图服务"**我该吵哪一场**"——它是选题层工具：先在地图上找到缝合线最密的主张簇和冲突最激烈的议题对，再钻进去开辩。这也直接衔接到选题环节的项目结论（甜区议题判定：条件依赖型 ≈ 哲学辨析型 > 价值表态型）。

## 2. 目标与非目标

**目标**

- G1 **横向结构可见**：同一主张跨议题的复现，必须由图上的实体承载，而不是文字描述。
- G2 **结构自涌现**：聚类、阵营分离、冲突张力由力学参数涌现，不靠手工摆位。
- G3 **真实性可追溯**：每个议题、每条论点都来自知乎真实检索，节点可回溯到原问题链接。
- G4 **可发布分享**：纯静态、零后端，一键发布在线链接供演示。
- G5 **检索经济**：在知乎 API 额度约束下通过"少搜多榨"策略产出足够规模的图。

**非目标（本期不做）**

- 节点编辑 / 新增（地图是**索引与浏览**层，内容生产在辩论间与辩论树）
- 时间维度（议题热度随时间变化）
- 判定任何主张对错，或给议题/主张排名（**永不做**，产品合法性底线）
- 跨议题关系的置信度交互式调节（本期用固定阈值 0.6）

## 3. 概念模型

### 3.1 节点类型（3 种）

| 类型 | 语义 | 深度 | 半径 | 填充 | 是否多父 |
|---|---|---|---|---|---|
| `cluster` 主张簇 | 跨议题归并后的同一主张 | 0（骨架） | 16 + min(缝合议题数,6)×2.6 | 蓝 #0f6fe5 / 红 #d9574d / 灰 #64748b | **是（2–6 个议题）** |
| `topic` 议题 | 一个知乎真实问题 | 1 | 11 + min(weight,5)×1.1 | 黑 #111827 | 否 |
| `claim` 论点 | 某议题下的一条真实主张 | 2 | 6.5 | 按立场：浅蓝 #7fb0f2 / 浅椒 #eda49c / 灰 #a8b6c8 | 否（唯一归属） |

> **关键设计决策：主张簇多父，论点单父。** 论点（claim）严格归属唯一议题——它是一条真实回答里的原话，不能跨议题复制。跨议题的"同一件事"由**上层的主张簇**承担：cluster 是归并产物，天然多父。这样既保住了原始数据的真实性（claim 可回溯到具体回答），又拿到了横向结构（cluster 缝合多议题）。这是本图与树的分水岭。

### 3.2 边类型（4 种）

| 关系 | 语义 | 距离 | 强度 | 颜色 / 线型 |
|---|---|---|---|---|
| `bridge` 缝合线 | 主张簇 ↔ 议题（跨议题横向关系） | 165 | 0.55 | **金色 #e8a33d，虚线 7 5，宽 2** |
| `rebuts` 冲突 | 论点 ↔ 论点，跨议题的实质反驳 | 250 | 0.08 | **红色 #d9574d，虚线 5 4，宽 1.6** |
| `member` 归属 | 论点 → 主张簇 | 78 | 0.9 | 灰蓝 #b9c6d4，实线，宽 1.1 |
| `contains` 包含 | 议题 → 论点 | 118 | 0.32 | 浅灰 #dbe3ec，实线，宽 0.8 |

> **设计决策：`rebuts` 刻意拉远、刻意放松。** 距离 250（全图最长）+ 强度 0.08（全图最弱）是反直觉的：通常我们希望"关系强 = 拉得近"。但矛盾在语义上是**排斥**关系，如果拉近就会塌成一团、看不出对抗。拉远之后，两条互相反驳的论点会各自留在自己的议题附近，中间绷出一条长长的红线——**张力被几何化了**。这条边是全图信息密度最高的元素，视觉上必须最醒目。

### 3.3 数据 Schema

```jsonc
// 节点（数据层，与渲染无关）
{
  "id": "cl-ai-only-replaces-execution",
  "kind": "topic | claim | cluster",
  "label": "AI只替代执行环节",
  "fullLabel": "…",              // topic 用：完整问题文本
  "summary": "…",                // cluster 用：主张簇释义
  "side": "positive | negative | neutral",
  "topicId": "zh-…",             // claim 用：唯一归属议题
  "reasonType": "技术壁垒 | 需求本质 | 责任归属 | 成本经济 | 教育培养 | 人类特质 | 行业周期 | 其他",
  "quality": 0.85,               // claim 用：LLM 评定的可辩论性 0–1
  "votes": 204,                  // claim 用：知乎赞同数（社区信号）
  "url": "https://www.zhihu.com/question/…",  // topic 用：可回溯
  "weight": 4,                   // topic 用：论点条数
  "topicCount": 6                // cluster 用：缝合议题数（决定半径）
}
// 边
{ "source": "cl-…", "target": "zh-…", "relation": "bridge | rebuts | member | contains" }
```

`src/types/map.ts` 中另有三层渲染副本类型 `MapSimNode` / `MapSimLink` / `MapResolvedLink`（见 §6）。

**为什么不复用 `DebateNode`**：`DebateNode` 只有一个 `parentId`，且语义是单场辩论的内部树。争议地图是**独立的图模型**，硬塞进树类型会立刻产生"多父怎么表示"的死结。

## 4. 交互规格

### F1 语义力学布局（P0，已实现）

不用一套统一参数，**按边的语义分别配力**——结构因此自己长出来，而不是被排出来：

| 力 | 参数 | 意图 |
|---|---|---|
| link distance | bridge 165 / member 78 / contains 118 / rebuts 250 | 关系越"密"越近；矛盾刻意最远 |
| link strength | bridge 0.55 / member 0.9 / contains 0.32 / rebuts 0.08 | 归属最硬，矛盾最软 |
| charge | cluster −1150 / topic −560 / claim −170 | 骨架撑开空间，论点紧凑成团 |
| collide | radius + cluster 34 / topic 22 / claim 13，strength 0.95 | 硬防重叠（骨架留更大缓冲） |
| **polarity（立场分离）** | forceX: positive −420 / negative +420 / neutral 0；strength: cluster 0.1 / 其余 0.035 | 同立场靠近，对立阵营自然分开 |
| center | forceCenter(0,0) | 防整体漂移，图心即原点 |

模拟参数：`alphaDecay 0.022`（收敛慢，留摆动余地）、`velocityDecay 0.42`。

初始撒点用**黄金角**（`angle = i×2.39996`, `r = 120 + √i×46`），避免所有节点叠在原点导致的初次爆炸。

### F2 拖拽（P0，已实现，核心手感）

- 按下：节点钉住（fx/fy），`alphaTarget 0.5` 维持拖拽期热度；alpha 低于 0.45 立即抬升，保证**按下即刻响应**。
- 拖动：节点跟手，同时按 `0.35` 系数把位移转成**直接邻居的速度冲量**——邻居被拽着走但不完全同步，保留自平衡。
- 松手：解钉回弹；位移不明显则视为**点击选中**。
- 坐标反解：屏幕坐标 → 减 zoom transform → 减画布中心偏移 → 模拟坐标，任意缩放级别下落点准确。

### F3 缩放平移（P0，已实现）

- d3.zoom，`scaleExtent [0.25, 3]`（比力导向图的 0.35 更宽——地图节点总数 43 更多，需要拉更远才能看全）。
- transform 作用于 `[data-zoom-layer]`，不改 SVG 尺寸。
- filter 拦截起点在 `[data-node-id]` 上的事件，避免与拖拽冲突；只响应左键；禁用双击缩放。
- 工具栏：− / +（步进 1.25×，180ms 过渡）、「重置视图」（zoomIdentity，240ms，同时 `alpha(0.6)` 让布局重新舒展）。

### F4 高亮（P0，已实现）

- `activeId = hover ?? selected`；高亮自身 + 一跳邻居。
- **边的点亮语义**：一条边被点亮，当且仅当**它的两个端点都落在高亮集合内**——注意这包含"两个邻居之间的边"，不只是与该节点直接相连的边。因此点开一个主张簇，会同时亮起它的所有议题、议题下的所有论点、以及**这些论点之间的所有冲突边**，等于一次点击就把"簇→议题→论点→冲突"整条证据链照亮。
- 未点亮节点淡化至 opacity 0.14，普通边 0.07、强调边 0.06。
- 选中节点带一圈高亮环（骨架=金色环，其余=蓝环）。
- 空白处点击取消选中。

### F5 标签分层（P1，已实现）

- 默认**只显示骨架标签**（cluster + topic），claim 标签仅在悬停/选中/被高亮时出现——43 个节点全标会糊。
- 「显示全部标签」开关可强制全显。
- 换行：中文按字符数切，最多两行，超出加省略号（cluster 9 字/行，其余 12 字/行）。

### F6 响应式（P1，已实现）

- ResizeObserver 监听容器（最小 320×360），尺寸变化时重设 viewBox 与中心，并轻推 `alpha(max(alpha, 0.15))` 让布局重新适配。
- **必须在 `typeof ResizeObserver !== "undefined"` 时使用，否则降级到 `window.resize`**（jsdom/老环境无此 API）。

## 5. 视觉规格

**形状承载身份**——用户一眼能分辨在看什么，不依赖图例：

- 主张簇 = **大圆**，半径随缝合议题数增长（缝合越多越大，视觉上"这条思想越通用"）
- 议题 = 中圆，深色
- 论点 = 小圆

**颜色承载立场**：蓝 = 正方，红/珊瑚 = 反方，灰 = 中性。同一立场被 polarity 力聚到一起，因此图上会自然形成**蓝色一侧 / 红色一侧**的宏观格局。

**线型承载关系强度**：缝合线金色虚线（宽 2）、冲突红色虚线（宽 1.6）、归属灰蓝实线、包含浅灰实线。缝合线与冲突单独渲染在一层（`.cm-links-emphasis`），**压在普通边之上、节点之下**，保证它们永不被遮住。

**渲染层级**：`.cm-links` → `.cm-links-emphasis` → `.cm-nodes`。

**标签**：字号 cluster 11.5 / topic 10.5 / claim 10；位置在节点下方 `radius + 13`；颜色 cluster `#7a4b00`（暖棕，配金色缝合线）、其余 `#334155`。

样式全部落在 `src/ui/styles.css` 的 `.controversy-map-*` / `.cm-*` 规则块，复用既有 `--debate-*` CSS 变量，含 `:root[data-theme="dark"]` 变体与 `max-width: 720px` 窄屏规则。

## 6. 技术架构与关键决策

架构：**React 管数据状态与 SVG 结构渲染，D3 管力模拟、坐标、拖拽、缩放**，职责严格分界。

### 6.1 四条铁律（沿用项目踩坑固化的结论）

1. **双层副本隔离**：d3 会就地改写传入对象（写 x/y/vx/vy，且 `forceLink` 把 `link.source` 从 id 字符串替换成节点对象引用）。数据层 `MapNodeData`/`MapEdgeData` **绝不**直接交给 d3，一律拷成 `MapSimNode`/`MapSimLink` 工作副本。
2. **id 快照先行**：
   ```ts
   // 必须在 forceLink.links() 之前快照，否则再也拿不到 id
   const linkSnapshot = links.map((l) => ({
     id: l.id, relation: l.relation,
     sourceId: l.source as string, targetId: l.target as string,
   }));
   simulation.nodes(nodes);
   linkForceRef.current?.links(links);   // ← 这一行会改写 l.source/target
   setSnapshot({ nodes, links: linkSnapshot });
   ```
3. **simulation 单例**：组件生命周期内只 `new` 一次，后续只做 `nodes()` / `links()` / `alpha().restart()`。
4. **每帧不走 setState**：tick 里 `syncDomPositions()` 直接写 DOM；React 只持有 `snapshot` 管**结构**（节点/连线增删），60fps 坐标更新零重渲染。

### 6.2 反模式表

| 反模式 | 后果 | 对策 |
|---|---|---|
| 数据层对象直接交给 d3 | React 状态被污染 | 工作副本拷贝 |
| 每帧 setState 同步坐标 | 卡死级重渲染 | DOM 直写 |
| simulation 重复创建 | 内存泄漏、alpha 行为不一致 | 单例 + restart |
| 忘记快照 link id | 连线增删后 DOM 错位 | `links()` 前快照 |
| `ResizeObserver` 未守卫 | jsdom/老环境直接崩溃 | `typeof` 判断 + `window.resize` 降级 |

> 第 5 条是**真实缺陷**：`DebateForceTree` 早已守卫，新写的 `ControversyMap` 漏了，测试时直接崩。**新增任何监听容器尺寸的组件都要照抄这个模式。**

### 6.3 数据管线（六步，全部可复现）

管线在 `research/controversy-map/`，中间产物全部落盘可复现：

| # | 脚本 | 职责 |
|---|---|---|
| 1 | `collect.ps1` | 调 `zhihu-cli search zhihu` 检索 5 组同域查询 |
| 2 | `parse.mjs` | 按 question id 聚合回答，抽首轮 claim + 社区信号 → `parsed.json` |
| 3 | `extract-claims.mjs` | **LLM 第一步**：每条回答 → 可辩论主张 + side + reasonType + quality → `claims.json`（带 `.claim-cache.json` 断点续跑） |
| 4 | `mine-cross.mjs` | **LLM 第二步（本图存在的理由）**：跨议题语义比对 → `cross-links.json` |
| 5 | `build-map.mjs` | **LLM 第三步**：同义标签归一成主张簇，组装最终图 → `map.json` |
| 6 | `build-ts.mjs` | 筛选 + 去重 + 生成前端模块 `src/data/controversyMap.ts` |

**关键算法决策**

- **两步法抽立场**（项目已验证的经验）：先逐条提炼主张+立场，再跨议题做语义比对。单步直判会导致标签碎片化（同一主张被写成十几个不同标签）。
- **先按 `reasonType` 粗分组，组内才两两比对**：23 条论点两两全比对是 253 对，噪音大且贵；按理由类型分组后只在同组内比对，因为"跨议题说同一件事"几乎必然共享理由类型。
- **只保留强关系**：LLM 输出 `same-claim | rebuts | related | unrelated`，只保留前两类且置信度 ≥ 0.6。
- **主张簇归一化的必要性**：LLM 给出的 label 存在同义异名（"程序员价值转向担责"/"人类核心价值在担责"/"AI时代核心价值是担责"实为同一主张）。不归一，图里会出现冗余网格边，力导向会把它拉成一坨。

### 6.4 检索经济性（额度约束下的策略）

知乎 API 有硬额度（`zhihu_search` 5000/日 但 `question_answers` 仅 **100**/日）。本期策略：

- **只用 `search zhihu`，不用 `question_answers`**。原因：`search zhihu` 返回的 `ContentText` 是**完整长文**，质量高于 `question_answers` 的 **200 字摘要**（后者还无作者、无赞同数）。
- 实测消耗：**5 次搜索（5/5000）**，`question_answers` 的 100 额度**零消耗**。
- 5 组查询刻意选**同域议题**（AI 与技术职业），使跨议题的 same-claim 关系**真实存在**而非硬凑。
