**版本** v1.0 · 2026-09-14
**项目归属** 知乎黑客松「灵魂匹配局：社区连接与兴趣社交」参赛作品
**文档定位** 初审评定重点考核项 —— 阐述项目核心创作思路、技术实现方案与社区生态契合度

## 一、项目概述

### 1.1 一句话定义

**争鸣（Dissensus）**：在知乎的问题社区上，用「辩论」替代「点赞」作为连接方式——把观点不同的人撮合到一起，用硬规则保证交锋质量，把每一次交锋沉淀为社区公共资产。

### 1.2 产品愿景

知乎是一个由「问题」组织的内容社区，用户在具体问题下因观点分化而聚集。然而，当前社区对「分歧」的处理方式只有两种：一是评论区对线（低质、无结构、无沉淀），二是站队投票（点赞/反对，信息量趋近于零）。争鸣要做的是第三种：**用辩论规则把分歧转化为结构化公共资产**，让对立的双方在交锋中留下可复盘的论点、证据与共识点。

### 1.3 核心问题诊断

| 现象 | 根因 | 争鸣的解法 |
|---|---|---|
| 评论区对线低质 | 无规则、无结构、无沉淀 | 五阶段轮次制 + 发言类型约束 + 对局报告 |
| 同一主张散落在多个议题下 | 数据结构是树（单父），无法表达横向关系 | 争议地图：主张簇（多父）+ 缝合边 + 冲突边 |
| 对立面无法被高质量连接 | 当前连接机制是兴趣/关注（同温层） | 选边制撮合：六维结构画像匹配，真人优先 Bot 兜底 |
|  debates 结束后观点流失 | 无持久化结构容器 | 辩论树：异步可续写的论点沉淀层 |

## 二、核心创作思路

### 2.1 三个底层洞察

#### 洞察一：知乎的组织原子是问题，不是兴趣圈

人们因一个**具体问题**聚集，观点天然分化——「程序员会不会被 AI 替代」「该不该劝人报计算机」这些问题天然就是辩题。然而知乎没有消费「分歧」的场所，分歧只沉淀为对线。争鸣把现成的分歧池转化为辩论撮合池。

#### 洞察二：对立面才是最高质量的社交对象

和观点相同的人聊天是回音室；和观点相反但表达相容的人交锋，才既有信息增量又有连接感。当前社区连接机制（关注、点赞、收藏）本质上是在强化同温层。争鸣用「选边制」把对立面撮合到同一局，用六维结构画像（逻辑、回应、证据、定义、修正、共识）匹配水平相近的人，避免碾压局与被碾压局。

#### 洞察三：对线之所以低质，是因为没有规则

没有「先理解对方」的强制、没有仲裁者的克制、没有沉淀结构——争鸣用产品机制补齐三件事：
- **理解对方**：质询轮必须针对对方立论结构的条目（定义 / 结论 / 理由）发问
- **克制仲裁**：Agent 永远只追问、不裁判；禁用词族「错误 / 谬误 / 输赢 / 对错」
- **沉淀结构**：对局报告 + 辩论树 + 争议地图，三层产出

### 2.2 产品哲学：四条红线

贯穿所有模块的不可动摇的原则：

1. **先承认，再推进**（D6 已拍板）：理解偏差由 Host 质询自然澄清，不做拦截式校验
2. **追问权替代验证权**：Agent 永远只追问、不裁判；体检输出的是追问点，不是判决书
3. **模拟与事实永远分离**：事件推演中，原作轨迹不展示、不注入模型，终局可选揭示
4. **不判输赢**：所有模块产出的是共识点、分歧点、追问清单，没有胜负

### 2.3 四种体验，一个底座

```
          ┌─────────────────────────────┐
          │   议题图谱（力导向聚类图）      │  ← 发现：真实议题的关系网络
          └──────────┬──────────────────┘
                     │ 选一个议题
       ┌─────────────┼─────────────────┐
       ▼             ▼                 ▼
┌────────────┐  ┌──────────────┐  ┌──────────────┐
│  实时辩论间  │→│    辩论树      │  │  事件推演      │
│  实时交锋    │  │  异步沉淀容器   │  │  单人历史扮演   │
└────────────┘  └──────────────┘  └──────────────┘
      分歧点 / 追问 回流辩论树；辩论间对局报告自带完整记录
```

| 模块 | 一句话 | 核心价值 |
|---|---|---|
| 辩论树 | 论点、证据、追问长成一棵人人可续写的树 | **异步沉淀容器**：让一场辩论的结构被后续的人继续使用 |
| 议题图谱 | 聚类布局的真实议题关系网络 | **选题工具**：让用户发现「该吵哪一场」 |
| 实时辩论间 | 围绕知乎问题临时开间，五阶段轮次制对局 | **高质量交锋**：硬规则保证交锋质量 |
| 事件推演 | 沉浸式历史角色扮演 | **单人深度体验**：让用户在具体情境中理解复杂决策 |

**两张图的分工**：
- **力导向图**（2026-09-13 已下线）：管**单议题内部**对垒结构感知
- **争议地图**：管**议题之间**的横向索引——同一主张跨议题的复现、跨议题的实质反驳

## 三、技术实现方案

### 3.1 整体架构

**三层分离架构**：

```
┌─────────────────────────────────────────┐
│  Presentation Layer (React + SVG)        │
│  - 数据状态管理（useState / useReducer）  │
│  - SVG 元素树渲染                          │
│  - 交互状态（hover / select / collapse）  │
└─────────────────────────────────────────┘
                    ↓ 单向数据流
┌─────────────────────────────────────────┐
│  Simulation Layer (D3 Force)             │
│  - 力模拟（charge / link / center）       │
│  - 拖拽行为（d3.drag）                    │
│  - 缩放行为（d3.zoom）                    │
│  - 每帧坐标更新（syncDomPositions）       │
└─────────────────────────────────────────┘
                    ↓ 工作副本
┌─────────────────────────────────────────┐
│  Data Layer (Immutable)                  │
│  - MapNodeData / MapEdgeData             │
│  - DebateNode / DebateEdge               │
│  - 不可变数据，绝不直接交给 D3            │
└─────────────────────────────────────────┘
```

**核心原则**：React 管数据状态与 SVG 结构渲染，D3 管力模拟、坐标、拖拽、缩放，职责严格分界。

### 3.2 四条铁律（踩坑固化的结论）

1. **双层副本隔离**：d3 会就地改写传入对象（写 x/y/vx/vy，且 `forceLink` 把 `link.source` 从 id 字符串替换成节点对象引用）。数据层 `MapNodeData`/`MapEdgeData` **绝不**直接交给 d3，一律拷成 `MapSimNode`/`MapSimLink` 工作副本。

2. **id 快照先行**：
   ```ts
   // 必须在 forceLink.links() 之前快照，否则再也拿不到 id
   const linkSnapshot = links.map((l) => ({
     id: l.id, relation: l.relation,
     sourceId: l.source as string, targetId: l.target as string,
   }));
   simulation.nodes(nodes);
   linkForceRef.current?.links(links);   // ← 这一行会改写 l.source/target
   setSnapshot({ nodes, links: linkSnapshot });
   ```

3. **simulation 单例**：组件生命周期内只 `new` 一次，后续只做 `nodes()` / `links()` / `alpha().restart()`。

4. **每帧不走 setState**：tick 里 `syncDomPositions()` 直接写 DOM；React 只持有 `snapshot` 管**结构**（节点/连线增删），60fps 坐标更新零重渲染。

### 3.3 关键模块实现

#### 3.3.1 争议地图（ControversyMap.tsx）

- **力模拟**：按边的语义分别配力（bridge / member / contains / rebuts 四类边独立参数）
- **立场分离力**：`forceX` 按立场（positive / negative / neutral）分配，同立场靠近、对立阵营自然分开
- **高亮语义**：一条边被点亮，当且仅当它的两个端点都落在高亮集合内——点开主张簇，同时亮起它的所有议题、论点、以及这些论点之间的所有冲突边
- **标签分层**：默认只显示骨架标签（cluster + topic），claim 标签仅在悬停/选中时出现

#### 3.3.2 实时辩论间（DebateRoom.tsx）

- **选边制撮合**：系统按议题给出预设正反方论点（来自争议地图管线），用户选边，真人优先 Bot 兜底
- **五阶段流程**：立论结构 → 质询轮（一问一答 ×2）→ 自由对辩 → 结辩 → 终局报告
- **Host 能力**：承认忠实度判定、追问生成、终局归纳
- **WebSocket 通信**：实时辩论间通过 zhengming-server 提供 WebSocket 服务

#### 3.3.3 辩论树（DebateTreePrototype.tsx）

- **异步可续写**：任何人可从树的任意节点加入，不需要从头读起
- **三层节点**：root（根主张）/ claim（论点）/ question（追问）
- **Agent 追问催化**：Agent 标记"未被回应的断言"并给出追问方向，用户一键以建议追问
- **深度约束**：深度上限 4 级，追问上限 3 条/节点

### 3.4 数据管线（争议地图）

争议地图的数据来自知乎真实检索，六步可复现管线：

| # | 脚本 | 职责 |
|---|---|---|
| 1 | `collect.ps1` | 调 `zhihu-cli search zhihu` 检索 5 组同域查询 |
| 2 | `parse.mjs` | 按 question id 聚合回答，抽首轮 claim + 社区信号 |
| 3 | `extract-claims.mjs` | **LLM 第一步**：每条回答 → 可辩论主张 + side + reasonType + quality |
| 4 | `mine-cross.mjs` | **LLM 第二步**：跨议题语义比对 → 发现 same-claim / rebuts |
| 5 | `build-map.mjs` | **LLM 第三步**：同义标签归一成主张簇，组装最终图 |
| 6 | `build-ts.mjs` | 筛选 + 去重 + 生成前端模块 `controversyMap.ts` |

**关键算法决策**：
- **两步法抽立场**（已验证）：先逐条提炼主张+立场，再跨议题做语义比对。单步直判会导致标签碎片化。
- **先按 reasonType 粗分组，组内才两两比对**：23 条论点两两全比对是 253 对，噪音大且贵；按理由类型分组后只在同组内比对。
- **主张簇归一化**：LLM 给出的 label 存在同义异名，不归一图里会出现冗余网格边。

### 3.5 检索经济性（知乎 API 额度约束）

- 知乎 API 硬额度：`zhihu_search` 5000/日，`question_answers` 仅 100/日
- **只用 `search zhihu`，不用 `question_answers`**：前者返回完整长文，质量高于后者的 200 字摘要
- 实测消耗：5 次搜索（5/5000），`question_answers` 额度零消耗
- 5 组查询刻意选**同域议题**（AI 与技术职业），使跨议题的 same-claim 关系真实存在而非硬凑

### 3.6 技术栈

| 层级 | 技术选型 | 说明 |
|---|---|---|
| 前端框架 | React 18 + TypeScript | 组件化开发，类型安全 |
| 可视化 | D3.js v7 | 力模拟、拖拽、缩放、SVG 操作 |
| 构建工具 | Vite | 快速热更新，生产构建优化 |
| 测试框架 | Vitest + Testing Library + jsdom | 26 项组件测试全绿 |

| LLM 接入 | StepFun / DeepSeek / GLM / Moonshot | Host 能力（追问生成、承认忠实度判定、终局归纳） |

## 四、与知乎社区生态的契合度与场景价值

### 4.1 生态契合度：为什么是知乎？

#### 契合点一：知乎的组织原子是问题

知乎不同于微博（以人为中心）、小红书（以兴趣标签为中心）、B站（以视频内容为中心），它的核心组织单元是**问题**。用户在问题下聚集，观点天然分化——这是现成的辩论撮合池。

- **甜区议题**：调研显示，「该不该 / 值得吗 / 会不会 / 能…吗」等句式天然适合辩论（条件依赖型 ≈ 哲学辨析型 > 价值表态型）
- **现成语料**：知乎问题下的长回答天然包含论点、证据、反驳，是辩论树和争议地图的原料库
- **可追溯性**：每条论点可回溯到原问题链接，保留社区公共资产的溯源属性

#### 契合点二：知乎的内容生命周期是长尾

知乎问题的热度周期远长于社交媒体的 24 小时热点。一个 2018 年的问题，2026 年仍然有新回答。这为辩论树提供了**持久沉淀**的场景——树不是一次性消耗品，而是长期存在的公共资产。

#### 契合点三：知乎用户的表达习惯是论证型

知乎用户的回答天然具有「论点 + 证据 + 推理」结构，这与辩论树的节点模型（claim + evidence + question）高度契合。不需要改造用户习惯，只需要把已有的论证结构可视化、可续写。

### 4.2 场景价值：四层价值

#### 价值层一：内容消费价值

**「分歧点回流辩论树」**——社区里最吵的地方，变成最有营养的地方。

传统评论区是对线的废墟，争鸣把它变成可导航的论证结构。用户可以：
- 看到一场辩论的完整结构（哪里一致、哪里分叉、哪里没被回应）
- 从任意节点加入，不需要从头读起
- 通过争议地图发现跨议题的深层分歧

#### 价值层二：连接价值

**「对立面才是最高质量的社交对象」**

当前社区连接机制（关注、点赞）强化同温层。争鸣用「选边制」把对立面撮合到同一局，用六维结构画像匹配水平相近的人：
- 匹配理由具体到观点：「你们都认同 X，但对 Y 的看法互补」
- 避免碾压局与被碾压局
- 真人对辩 → Bot 兜底，冷启动无压力

#### 价值层三：内容生产价值

**「让 AI 成为追问催化者，而不是裁判」**

- Agent 标记「未被回应的断言」并给出追问方向
- 用户一键以建议追问继续辩论
- 对局报告自动生成（质询记录 / 共识 / 分歧 / 未决 / 修正 / 定义分歧）

#### 价值层四：数据资产价值

**「跨议题争议地图」——发现「该吵哪一场」**

- 同一主张跨议题的复现由图上的实体承载
- 主张簇缝合多议题，发现「这条思想在哪些议题里被反复调用」
- 冲突边揭示跨议题的实质矛盾
- 「缝合度 × 冲突度」给议题对打分，自动推荐最值得开辩的议题组合

### 4.3 与知乎生态的协同路径

```
知乎问题
  ↓ [争议地图管线]
议题库 + 论点库 + 主张簇
  ↓ [选边制]
用户选边 → 六维画像匹配 → 真人优先 Bot 兜底
  ↓ [五阶段对局]
对局报告（质询记录 / 共识 / 分歧 / 未决 / 修正）
  ↓ [异步沉淀]
辩论树（论点 / 证据 / 追问）
  ↓ [跨议题挖掘]
主张簇（same-claim / rebuts）
  ↓ [选题推荐]
「该吵哪一场」建议
```

**数据闭环**：知乎问题 → 争鸣辩论 → 对局报告 → 辩论树 → 争议地图 → 选题推荐 → 知乎问题

### 4.4 差异化竞争力

| 维度 | 知乎现有机制 | 争鸣 |
|---|---|---|
| 分歧处理 | 评论区对线 | 五阶段轮次制辩论 |
| 连接方式 | 关注/点赞（同温层） | 选边制（对立面撮合） |
| 内容沉淀 | 时间线流 | 树状结构 + 跨议题地图 |
| AI 角色 | 无 | 追问催化者（不裁判） |
| 产物 | 碎片化评论 | 对局报告 + 辩论树 + 争议地图 |
